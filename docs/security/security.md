## 第1章 安全与保密性

## 概述

Linux一大核心特性是**多用户、多任务**，多用户可以同时在同一台计算机上工作。对用户而言，本地存储与网络上的数据在使用体验上几乎没有区别。

正因为多用户特性，必须隔离不同用户的数据，保障安全与隐私。同时需要保障数据在介质损坏（如硬盘故障）场景下依然可恢复。

本章重点聚焦**保密性与隐私防护**。一套完整安全体系还必须包含：定期更新、可用且经过验证的备份。没有备份，遭遇篡改或者硬件故障之后很难恢复数据。

> 
> 安全建议：采用**深度防御（defense‑in‑depth）**思路。不要指望单一防护手段可以完全保护系统与数据；多层防护叠加，大幅提升攻击者的入侵成本。

深度防御策略包含的组件：

- 密码哈希（PBKDF2、bcrypt、scrypt等算法加盐哈希）
- 数据加密（AES等）
- 日志记录、监控、入侵检测
- 防火墙
- 杀毒扫描软件
- 成文的应急处置流程
- 数据备份
- 物理安全防护
- 安全审计、漏洞扫描、渗透测试

openSUSE Leap内置大量软件可以满足上面的安全需求，下面是各安全方向入门指引。

## 密码

Linux系统**不会保存明文密码**，只存储密码哈希值。哈希是单向算法，把原始数据转换为不可逆数字指纹。
密码哈希保存在`/etc/shadow`，普通用户无法读取该文件。

> 
> 算力足够的条件下哈希依然可以被暴力破解，因此哈希文件本身不能对普通用户开放访问。

美国国家标准与技术研究院NIST发布密码规范指南：
[https://pages.nist.gov/800‑63‑3/sp800‑63b.html#sec5](https://pages.nist.gov/800%E2%80%9163%E2%80%913/sp800%E2%80%9163b.html#sec5)

密码策略配置参阅本章“密码设置”小节；认证完整内容见第一部分《认证》。

## 备份

系统被入侵时，备份可以用来恢复到系统未被篡改的状态。遇到Bug、误操作，备份也可以用来对比当前系统与历史正常状态差异。

生产环境强烈建议**异地备份**，防范火灾、水灾等灾难。

部分企业组织受合规约束，不能无限制备份、无限期留存数据。纸质文档有销毁策略，Linux备份介质也应当配套对应策略。

备份介质同样需要重视物理安全，**建议对备份数据加密**。可以对单个备份归档加密，也可以加密整个备份文件系统。备份介质丢失、备份服务器被攻陷时，加密可以保护数据。加密同时也要保证应急场景下有权限人员可以解密；同时要考虑密钥泄露需要更换密钥的场景。

> 
> 如果怀疑系统已经被入侵，必须校验备份完整性。如果入侵长期未被发现，备份内部很可能已经被植入篡改后的配置、恶意程序。保留足够长周期备份历史，便于排查异常改动。
> 即使没有发生安全事件，定期对比备份内关键配置文件差异，有助于提前发现安全问题，适合改动频率不高的文件。

## 系统完整性

攻击者如果可以物理接触服务器，能够篡改固件、引导流程，在合法用户开机时获取权限。不是所有服务器都可以放置在上锁机房，但物理上锁机房是第一道防线。
退役设备处理也必须安全。加固引导加载程序、限制可移动介质访问同样属于物理安全范畴，详见第9章《物理安全》。

推荐加固措施：

1. 禁止从可移动介质引导系统
2. UEFI密码、安全启动Secure Boot、GRUB2密码保护引导流程> 
> Linux引导加载程序可以向内核传递启动参数。设置引导密码非常关键。内核本身以root权限运行，系统启动阶段内核是root权限的源头。参考参考手册“GRUB2引导加载程序”章节设置引导密码。
3. 开启磁盘加密，参阅第12章《分区与文件加密》
4. 服务器存储加密可以使用cryptctl，参阅第13章
5. 使用AIDE检测系统文件篡改，参阅第20章《AIDE入侵检测》

## 文件访问

Linux“一切皆文件”设计理念，文件权限是访问控制核心。普通文件、目录、硬件设备都依靠权限控制访问。大部分硬件设备默认仅root可访问；串口等部分设备普通用户也可以访问。

> 
> 安全原则：执行任务使用**最小权限**。例如阅读邮件完全不需要root账号。一旦程序存在Bug，漏洞就拥有该程序运行账号的全部权限；最小权限原则可以缩小攻击面，降低破坏范围。

基础权限参阅“传统文件权限”“ACL访问控制列表”章节。
AppArmor、SELinux可以对应用、用户施加额外约束，见第四部分《AppArmor》、第五部分《SELinux》。

如果设备可以通过Live系统、拆下硬盘等方式绕过操作系统读取磁盘，务必加密磁盘。openSUSE支持操作系统盘、数据盘加密。

## 网络

加固网络服务是安全工作重中之重，尽可能在OSI模型多层同时做防护。
所有通信尽量使用现代加密算法在传输层/应用层完成认证加密；VPN可以在物理网络之上增加一层安全隧道。

openSUSE网络安全手段：

1. openssl生成X509证书，用于各类服务加密与身份认证；自建CA证书颁发机构。参考`man openssl`。
2. 部分网络暴露公网互联网。防火墙关闭不必要端口，卸载、禁用不需要的服务，缩小攻击面，参阅第23章《地址伪装与防火墙》。
3. OpenVPN搭建VPN，参阅第24章《配置VPN服务器》。
4. 网络服务启用强身份认证，参阅第一部分《认证》。

## 恶意软件

恶意软件包含病毒、蠕虫、勒索软件、Rootkit，目的是破坏系统或者窃取数据。一部分恶意软件利用软件漏洞入侵；更多场景是用户执行了来源不明第三方软件。

openSUSE官方软件源提供大量软件包，减少下载第三方二进制程序的需求。SUSE提供的RPM包带有数字签名，包管理器校验签名保证完整性。

```
rpm --checksig 包名.rpm
```

签名公钥位于第一张安装DVD，也可以从公钥服务器获取。

可以使用ClamAV杀毒软件扫描恶意代码，可集成邮件服务器、HTTP代理，在恶意内容抵达用户前拦截。
严格的用户权限策略，也可以降低意外执行恶意代码带来的风险。

## 重要安全小贴士

1. 跟进最新安全动态，收到安全公告尽快安装对应更新
2. 尽量避免root账号操作；设置严格文件权限
3. 网络通信优先使用加密协议
4. 禁用所有非必需网络服务
5. 定期安全审计，扫描开放端口
6. 使用AIDE监控系统文件完整性
7. 谨慎安装第三方软件
8. 定期校验备份可用性
9. 定期审查系统日志（logwatch等工具）
10. 防火墙策略：默认拒绝，仅白名单放行必要端口
11. 安全措施设计冗余，多层防护
12. 笔记本等移动设备尽量开启磁盘加密

## 上报安全问题

发现安全漏洞，首先确认是否已有更新包。若无可用更新，发送邮件至 [security@suse.de](mailto:security@suse.de)，详细描述问题、受影响软件包版本。推荐邮件使用GPG加密。

# 第一部分 认证

## 第2章 使用PAM可插拔认证模块

> 
> **摘要**
> Linux使用PAM（可插拔认证模块）作为中间层，在用户与应用程序之间处理认证。PAM模块系统全局可用，各类应用都可以调用。本章介绍模块化认证工作原理以及配置方式。

### 什么是PAM？

系统管理员、开发者经常需要限制系统访问，或者限制程序功能。没有PAM的情况下，每当引入LDAP、Samba、Kerberos这类新认证方式，所有应用都必须单独修改适配，耗时而且容易出错。

PAM将**应用程序和认证机制解耦**，认证逻辑交给集中管理模块。新增认证方式，只需要编写、配置对应的PAM模块，应用程序无需改动。

PAM概念组成：

1. **PAM模块**：共享库，实现某一类认证逻辑
2. **模块栈**：一个或多个PAM模块按顺序组成处理栈
3. **支持PAM的服务**：调用模块栈完成认证的程序，例如`login`、`sshd`。特殊服务名`other`作为默认兜底规则。
4. **模块参数**：传给单个PAM模块的参数，改变模块行为
5. **结果评估机制**：处理每个模块返回值。成功继续下一个模块；失败根据配置分为：不影响继续执行、立刻终止等多种策略。

### PAM配置文件结构

openSUSE Leap不使用旧式单文件`/etc/pam.conf`，采用**目录式配置**：`/etc/pam.d/`目录。
每一个支持PAM的服务，在该目录拥有独立配置文件。例如sshd的PAM配置：`/etc/pam.d/sshd`。

配置文件每行最多4个字段：
`类型 控制标记 模块路径 模块参数`

#### TYPE 类型

PAM模块按栈处理，四种模块类型，职责各不相同。

1. **auth**：校验用户身份。传统方式询问密码；也可以使用芯片卡、生物识别（指纹、虹膜）。
2. **account**：校验账号是否有权限使用该服务。例如检查账号是否过期。
3. **password**：修改认证令牌，一般用于修改密码。
4. **session**：会话管理。认证前后执行，记录登录事件、配置用户环境（家目录、邮件、系统资源限制）。

#### CONTROL 控制标记

控制模块返回结果的处理逻辑：

1. **required**：该模块必须执行成功认证才能继续。模块失败之后，依然会继续执行同类型其余全部模块，全部跑完之后才向用户返回认证失败。
2. **requisite**：同样要求模块执行成功。一旦失败，**立刻返回错误，不再运行后续模块**；成功则继续后续模块。适合前置校验必要条件。
3. **sufficient**：该模块成功，直接认证通过，跳过后面其余模块；失败则继续执行后续模块。
4. **optional**：模块结果不决定认证成功失败，仅做附加操作。

#### MODULE_PATH 模块路径

PAM模块库文件路径。

#### MODULE_ARGS 模块参数

传递给模块的自定义参数。

### sshd 的PAM配置示例

文件 `/etc/pam.d/sshd`

```
#%PAM‑1.0
auth     include        common‑auth
account  include        common‑account
session  include        common‑session
password include        common‑password
```

`include`语法：引入公共配置片段，公共配置存放在`common‑auth`、`common‑account`、`common‑session`、`common‑password`，实现多个服务复用同一套认证策略。

### PAM模块配置文件

#### pam_env.conf

设置登录会话环境变量。可以根据用户、远程主机设置环境。

#### pam_mount.conf.xml

登录时自动挂载文件系统，登出自动卸载。支持本地、网络文件系统。

#### limits.conf

`/etc/security/limits.conf`，配置用户/用户组资源软硬限制：最大进程数、打开文件句柄数、内存占用、CPU等。

### 使用 pam‑config 配置PAM

`pam‑config`是openSUSE提供工具，修改`common‑*`公共PAM配置片段。支持启用/禁用LDAP、Kerberos、Samba、U2F等认证后端。
交互式运行：

```
sudo pam-config
```

命令行非交互示例：

```
sudo pam-config --add --u2f
sudo pam-config --delete --krb5
```

### 手动配置PAM

> 
> ⚠警告：错误修改PAM配置，会导致全部账号无法登录系统。修改前务必备份配置文件，保留一个root本地终端会话，出现故障方便回滚。

直接编辑`/etc/pam.d/`下面的配置文件，或者修改`common‑*`公共包含文件。修改完成立刻生效，不需要重启守护进程。

### 配置U2F密钥本地登录

U2F安全密钥（YubiKey等）用于本地系统登录认证。

#### 将U2F密钥绑定用户账号

安装软件包`pam‑u2f`，为用户生成u2f密钥映射文件`~/.config/Yubico/u2f_keys`。

```
pamu2fcfg > ~/.config/Yubico/u2f_keys
```

> 
> 执行时按U2F设备按键确认。多个密钥用追加模式`>>`。

#### 更新PAM配置

编辑`/etc/pam.d/common‑auth`，在合适位置添加：

```
auth    sufficient    pam_u2f.so
```

> 
> 测试：新开终端执行`su ‑ 用户名`，验证U2F登录是否正常，**不要关闭现有会话**。

更多信息参阅`man pam_u2f`。

## 第3章 使用NIS网络信息服务

> 
> NIS（Network Information Service），网络信息服务，集中管理用户、组等系统账号数据库，多台机器共享一份账号数据。

### 配置NIS服务器

#### 搭建NIS主服务器

1. 安装`ypserv`软件包
2. 设置NIS域名`/etc/defaultdomain`
3. YaST → 网络服务 → NIS服务器，选择主服务器模式，配置域名、允许客户端网段。
4. 初始化NIS数据库，启动`ypserv`、`yppasswdd`服务，设置开机自启。
5. 防火墙开放NIS端口。

#### 配置NIS从服务器（Slave）

从服务器作为备份，同步主服务器NIS数据库，分担查询负载。

1. 从服务器设置相同NIS域名
2. YaST NIS服务器选择从服务器模式，填写主服务器IP。
3. 主服务器配置允许从服务器做数据库拉取。
4. 启动服务，执行数据库推送同步。

### 配置NIS客户端

客户端机器接入NIS域，使用NIS账号登录本机。
YaST → 网络服务 → NIS客户端。设置NIS域名，填写NIS服务器地址；可以开启广播自动查找NIS服务器。同时配置nsswitch.conf，让系统优先查询NIS账号数据库。

> 
> 注意：NIS协议本身**不加密**，内网使用，不建议公网暴露。

## 第4章 使用YaST配置认证客户端

> 
> 摘要：YaST图形界面配置LDAP、NIS、Active Directory客户端，SSSD作为后端。

### 使用YaST配置认证客户端

YaST → 用户与组 → 认证客户端。支持选择后端：NIS、LDAP、Active Directory。配置参数写入`/etc/sssd/sssd.conf`。

### SSSD（System Security Services Daemon）系统安全服务守护进程

SSSD作为中间守护进程，本地缓存远程身份数据。

1. **状态查看**

```
systemctl status sssd
sssctl domain‑list
```

2. **缓存机制**：远程账号信息本地缓存。网络断开时，依然允许已缓存账号登录本机（离线登录）。缓存超时时间可以配置。
清除缓存：停止sssd，删除`/var/lib/sss/db/*`，重启服务。

## 第5章 LDAP与389 Directory Server

> 
> 389‑DS是开源企业级LDAP目录服务器，用于集中存储账号、用户组、联系人等目录数据。替代OpenLDAP。

### LDAP目录树结构

DN区分名、RDN相对区分名、后缀（suffix）、对象类、属性。目录树层级组织条目。

### 使用Docker容器部署389 Directory Server

可以使用容器快速部署测试实例。

### 安装389 Directory Server

1. 安装软件包`389‑ds`。
2. 创建实例：`dscreate`工具，三种方式：交互式向导、自定义配置文件、模板创建实例。

```
dscreate from‑file inst.inf
```

实例会创建独立系统用户，监听389端口；TLS加密监听636端口。

### 启停389‑DS实例

```
systemctl status dirsrv@实例名
systemctl start dirsrv@实例名
systemctl stop dirsrv@实例名
```

### 设置管理员账号凭据

目录管理员DN默认`cn=Directory Manager`，设置密码。

### 防火墙配置

开放389（ldap）、636（ldaps）端口。

### 389‑DS备份与恢复

1. **备份LDAP服务配置**：备份`/etc/dirsrv/`实例配置目录。
2. **离线数据库备份恢复**：数据库停止状态下db2bak备份；bak2db恢复。
3. **在线热备份**：数据库运行状态下执行备份，无需停机。备份文件存放在实例配置指定路径。

### LDAP用户与组管理

命令行工具`dsctl`管理用户、用户组。

- 查询用户、组条目
- 创建用户，修改密码
- 创建管理用户组，添加移除组成员
- 删除用户、组

### 插件管理

启用、禁用LDAP插件。部分插件389‑DS不支持。

### 使用SSSD对接LDAP认证

客户端SSSD配置连接389‑DS，实现LDAP账号登录本地机器。注意部分旧密码哈希算法不再支持。

### 从OpenLDAP迁移到389 Directory Server

## 第6章 Kerberos网络认证

> 
> Kerberos：网络环境安全身份认证协议，基于票据机制，避免网络传输明文密码。

### 概念总览

#### Kerberos术语

- KDC：密钥分发中心，包含认证服务AS、票据授予服务TGS
- Realm：Kerberos域，大写域名，如`EXAMPLE.COM`
- Principal：主体账号，用户主体、服务主体
- TGT票据授予票据；服务票据ST

#### Kerberos工作流程

1. **首次联系KDC**：客户端向AS请求TGT票据；使用密码解密返回的TGT。
2. **申请服务票据**：客户端拿着TGT向TGS请求访问某个服务的服务票据。
3. **双向认证Mutual authentication**：客户端出示服务票据访问业务服务；服务向客户端证明自身身份，防止钓鱼服务。
4. **票据授予，联系业务服务器**。

用户视角：登录获取票据凭证，访问各类Kerberos化服务，不需要重复输入密码。`kinit`获取票据，`klist`查看票据。

### 安装部署Kerberos

1. **网络拓扑规划**：KDC服务器、客户端；规划Realm域名。
2. KDC硬件规划。
3. **时间同步**：Kerberos强依赖时间，必须部署NTP，时间偏差过大票据直接失效。
4. **配置KDC服务器**：`krb5‑kdc`软件包；修改`krb5.conf`、`kdc.conf`；创建数据库，设置数据库主密码。启动krb5kdc、kadmin服务。
5. **配置Kerberos客户端**，修改`/etc/krb5.conf`，指向KDC地址。
6. **远程KDC管理**：kadmin远程管理；配置ACL权限。
7. **创建服务主体（service principal）**，给各个网络服务生成票据主体。
8. **PAM启用Kerberos认证**，客户端登录使用Kerberos账号。
9. **SSH配置Kerberos GSSAPI认证**，免密码SSH登录。
10. **LDAP + Kerberos结合**，LDAP存储账号，Kerberos做认证。
11. **Kerberos与NFS**：NFS使用Kerberos安全认证，NFSv4推荐。处理组成员关系。

### 性能与可扩展性

主KDC、多Realm域、域信任关系配置。

# 第7章 活动目录支持
## 将Linux与活动目录环境集成
### Linux对活动目录支持的背景信息
#### 域加入
将Linux主机加入Windows活动目录（AD）域之后，该主机就可以识别AD的用户、用户组、组策略。主机会从域控制器获取身份信息，不再只依赖本地`/etc/passwd`与`/etc/group`。

#### 域登录与用户家目录
AD域用户登录Linux客户端时，系统可以动态创建用户家目录。家目录既可以存储在本地磁盘，也可以挂载网络共享目录。如果离线，客户端依然可以使用缓存凭证完成登录。

#### 离线服务与策略支持
即便暂时无法连接域控制器，SSSD可以使用本地缓存的身份凭证与策略，允许域用户正常登录系统。待网络恢复后，会同步最新的域策略信息。

### 为活动目录配置Linux客户端
#### 选择用于连接活动目录的YaST模块
有两个YaST模块可以完成AD域接入，二者底层组件不一样：
1. **用户登录管理（User logon management）**
底层基于SSSD。绝大多数接入活动目录的场景推荐使用该模块。
2. **Windows域成员身份（Windows domain membership）**
底层基于winbind。当需要NTLM认证或者跨林信任功能时选用此模块。

#### 使用“用户登录管理”加入活动目录
1. 打开YaST → 用户登录管理。
2. 选择加入域，填写活动目录域名、域控制器地址、拥有域加入权限的AD管理员账号与密码。
3. 确认配置，完成域加入。SSSD服务会自动生成配置文件并启动。

#### 使用“Windows域成员身份”加入活动目录
1. 打开YaST → Windows域成员身份。
2. 填入AD域名、域控制器地址、有权限加入计算机的AD账号密码。
3. 该模块使用Samba‑winbind组件完成域集成。

#### 检查活动目录连接状态
- 使用SSSD：执行 `systemctl status sssd`，查看服务状态；使用`id 域用户名`验证能否解析AD用户信息。
- 使用winbind：执行 `systemctl status winbind`；使用`wbinfo -u`列出域内用户，确认连通。

### 登录到活动目录域
#### GDM图形登录
在GDM登录界面，使用格式 `域\用户名` 输入账号，输入AD用户密码即可登录。客户端会自动解析域身份。

#### 控制台登录（TTY）
在文本控制台，输入账号格式 `域\用户名`，填写AD密码登录。如果开启家目录自动创建，首次登录会生成用户家目录。

#### 修改密码
- 在线模式：可以使用`passwd`命令，密码修改请求会提交给AD域控制器。
- 离线缓存状态下**无法修改密码**，必须连通域控制器才可以更新AD账号密码。

### 活动目录证书自动注册
#### 在服务端配置证书自动注册
在Windows活动目录证书服务（AD CS）中配置证书注册策略，定义下发给Linux客户端的证书模板，设置证书用途、有效期、访问权限。

#### 在客户端启用证书自动注册
Linux客户端配合SSSD，可从AD获取自动颁发的证书。证书可以用于TLS认证、智能卡登录等场景。证书到期前，客户端会自动向AD‑CS发起续期请求。

# 第二部分 本地安全
## 第9章 物理安全
### 系统锁
如果攻击者能够物理接触计算机硬件，就可以篡改固件以及引导流程，在合法用户开机启动机器时获取系统访问权限。并非所有计算机都可以安置在上锁的机房内，但首要防护措施应当是对服务器机房进行物理上锁。

同时，报废旧设备时必须采用安全的处置方式。保护引导加载程序、限制可移动介质的访问权限同样能够实现有效的物理安全防护。更多信息请参见第9章《物理安全》。

你可以考虑实施以下额外防护措施：
- 将系统配置为禁止从可移动设备引导；
- 使用UEFI密码、安全启动以及GRUB2密码保护引导流程。

Linux系统由引导加载程序启动，引导加载程序允许向待启动的内核传递额外参数。你可以为引导加载程序设置密码，阻止其他人在引导阶段使用这类参数。**这对系统安全至关重要**：内核本身以root权限运行，同时它也是系统启动阶段授予root权限的首要控制点。

关于在引导加载程序中设置密码，可参阅参考文档《参考指南》中“GRUB2引导加载程序”章节的“设置引导密码”小节。
- 启用磁盘加密。更多信息参见第12章《加密分区和文件》。
- 使用cryptctl对托管存储进行加密。更多信息参见第13章《使用cryptctl实现托管应用存储加密》。
- 使用AIDE检测系统配置发生的任何变更。更多信息参见第20章《使用AIDE实现入侵检测》。

### BIOS锁定
对BIOS/UEFI设置密码。该设置可以阻止未授权人员修改启动顺序、关闭安全启动、篡改固件选项。如果没有BIOS密码，攻击者可以通过外置介质引导系统，直接读取硬盘的全部数据。

### 通过引导加载程序加固安全防护
可以为GRUB2引导程序设置密码保护。在没有密码的情况下，攻击者能够在开机菜单传入自定义内核参数，直接获取root权限。引导密码可以阻止未授权用户修改内核启动参数。

### 处置存有敏感数据的退役Linux服务器
简单删除文件或者格式化磁盘，无法彻底销毁数据，数据依旧可以被数据恢复工具读取。服务器报废或者移交之前，必须彻底擦除磁盘当中的敏感信息。

#### scrub：磁盘覆写工具
`scrub`是磁盘覆写工具，它会对磁盘分区或者整块磁盘执行多次覆写操作，使用随机数据填充存储介质，清除原有残留数据，防范数据被恢复。

#### 限制可移动介质访问
管控U盘、移动硬盘这类外接存储设备。既可以防止内部数据被非法拷贝外泄，也能够避免恶意U盘带入恶意代码。

### 使用USBGuard强制USB设备授权，保护系统
USBGuard实现USB设备白名单机制：只有被显式允许的USB硬件，才能够被系统识别并使用。

#### 安装USBGuard
安装usbguard软件包，并且启用对应的systemd服务。
#### USBGuard使用方式
生成设备策略规则；维护允许列表与拒绝列表；查看USB设备事件；调试策略规则。
#### 更多信息
查阅对应的man手册以及项目文档。

## 第11章 文件管理
Linux奉行“一切皆为文件”的设计理念，因此文件权限是本地安全的基础。文件权限控制普通文件、目录乃至硬件设备的访问权限。默认情况下，绝大多数硬件设备只允许root访问，但是部分设备（例如串口）允许普通用户进行访问。

### 磁盘分区
合理规划磁盘分区：将`/home`、`/tmp`、`/var`和根目录`/`分开挂载。防止某一个目录（例如日志、临时文件）写满耗尽整块磁盘的可用空间；同时，可以为不同分区单独设置挂载安全参数，例如`noexec`、`nosuid`，以此提升系统安全性。

### 修改部分系统文件权限
检查关键系统文件的权限。权限过宽会带来安全风险，需要把权限收紧至业务运行所需的最小范围。

### 将家目录权限从755修改为700
- `755`权限：系统内其他用户可以读取、浏览家目录内部的文件；
- `700`权限：**仅文件属主本人拥有读写访问权限**，其他任何用户完全无法访问该家目录。

建议将普通用户家目录的权限设置为700，避免隐私文件被系统内其他用户读取。

### 默认umask
umask定义新建文件、目录的默认权限掩码。

#### 调整默认umask
修改全局umask配置，使新建文件与目录的默认权限更加严格，减少权限过宽带来的问题。

### SUID / SGID 文件
SUID即设置用户ID位；SGID即设置组ID位。
设置SUID位的程序，在运行的时候会临时拥有该文件属主的权限（典型例子：`passwd`命令）。系统当中多余、存在疑点的SUID/SGID文件属于高危风险点，需要定期扫描审计。

### 全局可写文件（World‑writable files）
全局可写文件代表系统中任意用户都可以读写修改该文件，存在被篡改的风险。定期查找系统内的全局可写文件，确认其存在的必要性。

### 无属主/无属组文件
文件的UID、GID指向已经被删除的用户或者用户组。这类孤儿文件需要检查并处置，防止被攻击者利用。

# 第12章 加密分区和文件
## 12.1 使用YaST设置加密文件系统
你可以借助YaST，在系统安装阶段或者已经完成安装的系统中，对分区或者部分文件系统进行加密。不过，在已运行的系统中对现有分区加密难度更高，因为该操作需要调整并修改现有分区大小与布局。遇到这类场景，创建一个指定大小的加密文件容器，用来存放其他文件或者部分文件系统内容，会更加便捷。

如果要对一整个分区加密，需要在分区规划中专门划出一个分区用于加密。YaST给出的标准分区方案默认不会包含加密分区，你必须在分区对话框中手动添加加密分区。

### 12.1.1 在系统安装期间创建加密分区
> **警告：密码录入**
务必牢牢记住加密分区的密码。没有该密码，你将无法访问、也无法恢复加密分区内的数据。

YaST专家分区对话框提供创建加密分区所需的全部选项。按下面步骤新建加密分区：
1. 依次点击**系统 › 分区程序**，打开YaST专家分区工具。
2. 选中一块硬盘，点击**添加**，选择主分区或者扩展分区。
3. 设置分区大小，指定磁盘上要使用的空间范围。
4. 选定文件系统类型，并设置该分区的挂载点。
5. 勾选**加密设备**复选框。

> **注意：需要额外软件包**
勾选“加密设备”之后，会弹出窗口提示安装附加软件。请确认安装全部所需软件包，保证加密分区可以正常工作。

如果该加密文件系统不需要开机自动挂载，在fstab选项里勾选**不挂载此分区**。反之，勾选**挂载分区**并填写挂载点。

点击**下一步**，输入该加密分区的访问密码。输入的密码不会回显到屏幕；为防止输入错误，需要连续输入两次密码。

点击**完成**结束配置，全新的加密分区就此创建完毕。

系统开机时，如果检测到`/etc/fstab`里配置了开机自动挂载的加密分区，会在挂载前要求输入密码。密码校验通过完成挂载后，该分区就可以被所有用户访问使用。

如果你不想在本次启动过程挂载加密分区，在密码提示界面直接按下回车，当系统再次询问密码时选择拒绝。此时加密文件系统不会被挂载，系统会继续启动，但分区内的数据将无法访问。

想要挂载一个没有设置开机自动挂载的加密分区，可以打开文件管理器，在位置面板点击该分区条目，系统会弹窗要求输入密码，验证通过后完成挂载。

> 补充说明：如果你是在一块已经存在分区的磁盘上执行系统安装，也可以在安装流程中对已有分区进行加密。操作参考12.1.2小节，但请注意：该操作会销毁分区上全部原有数据。

### 12.1.2 在运行中的系统上创建加密分区
> **警告：在运行系统上启用加密**
在正在运行的系统中也能够创建加密分区。但对已有分区执行加密会销毁分区内所有数据，同时还需要调整、重构现有分区布局。

在运行中的系统执行如下操作：
1. 在YaST控制中心打开**系统 › 分区程序**，弹出确认框点击“是”继续。
2. 在专家分区器界面选中需要加密的分区，点击**编辑**。
3. 后续操作流程，和12.1.1“在安装过程中创建加密分区”完全一致。

### 12.1.3 加密可移动介质内容
YaST对待外置硬盘、U盘这类可移动介质，处理逻辑和普通内置磁盘分区完全一致。你可以把可移动设备上整个分区设置为LUKS加密。

当加密完成之后，每次把移动介质插入计算机，系统都会提示输入解密密码。输入正确密码之后，介质才可以被挂载、读取。一旦介质丢失或者被盗，加密可以保护介质内部的机密文件不会被未经授权的人员读取。

> 提示：可移动介质加密完成之后，不要忘记备份解密密码或者备份LUKS密钥槽。如果遗忘密码，介质内全部数据将无法恢复。

## 12.2 使用GPG加密文件
GPG（GnuPG）是一套实现OpenPGP标准的加密工具集，可用于对单个文件进行非对称加密，也可以用于加密电子邮件。

你既可以使用公钥对文件加密，只有对应的私钥持有者才能够解密读取；也可以使用对称加密模式，依靠一个密码完成加密和解密。

- 对称加密示例（密码加密）：
```bash
gpg -c example.txt
```
该命令会生成加密后的文件`example.txt.gpg`。解密命令：
```bash
gpg example.txt.gpg
```

- 公钥加密示例：
```bash
gpg -r 接收方ID --encrypt example.txt
```

GPG同时支持签名操作，用来校验文件完整性、确认文件来源没有被篡改。更多参数与用法，请参阅`man gpg`手册页。

## 12.3 使用Rage加密文件
Rage是加密工具`age`的Rust语言实现，是一款现代、简洁的文件加密工具。age系列工具采用简洁的密钥格式，没有复杂的证书体系，适合日常本地文件加密场景。

可以使用rage完成文件对称密码加密，或者使用age公钥进行非对称加密。

密码加密示例：
```bash
rage -o example.age example.txt
```
解密：
```bash
rage -d -o example.txt example.age
```

> 注意：rage并不处理磁盘分区，仅用于对单个文件做加密，不能直接生成LUKS加密块设备。

## 12.4 补充资源
- `man cryptsetup`：LUKS磁盘加密工具手册；
- `man gpg`：GnuPG手册；
- `man rage`：rage加密工具手册；
- openSUSE官方安全手册在线网页，查看加密相关的更多提示、故障排查内容。

# 第13章 使用cryptctl实现托管应用的存储加密
cryptctl适用于服务器环境下LUKS加密磁盘的集中管理。客户端主机的加密磁盘解密密钥存储在独立的cryptctl服务端。客户端开机时连接服务端获取密钥，完成磁盘解锁。密钥不会保存在客户端本地，该方案非常适合云主机与托管服务器。

## 13.1 搭建cryptctl服务端
cryptctl‑server集中保存所有客户端LUKS解密密钥，并且校验客户端身份，只有合法客户端才可以获取对应解密密钥。

1. 在服务端安装软件包`cryptctl‑server`。
2. 编辑服务端配置文件`/etc/cryptctl/server.conf`，配置监听地址、TLS证书、客户端认证策略。
3. 启用并启动`cryptctl‑server` systemd服务。
4. 开放防火墙对应端口，允许客户端网络访问服务端。

> **重要提示**：cryptctl服务端本身必须做好磁盘加密。如果服务端磁盘泄露，所有客户端解密密钥都将面临泄露风险。

## 13.2 搭建cryptctl客户端
每一台托管的Linux主机作为cryptctl客户端，开机阶段向cryptctl服务端请求LUKS密钥。
1. 客户端安装软件包`cryptctl‑client`。
2. 修改客户端配置`/etc/cryptctl/client.conf`，填写cryptctl服务端地址、TLS证书路径、客户端唯一身份标识。
3. 将客户端注册到cryptctl服务端，服务端保存该客户端的LUKS密钥副本。

> 注意：客户端本地不再保存LUKS密钥。一旦网络无法连通cryptctl服务端，主机无法自动解锁磁盘。

## 13.3 在/etc/fstab中配置LUKS卷
除cryptctl配置外，还需要正确配置`/etc/crypttab`与`/etc/fstab`。
- `/etc/crypttab`定义加密块设备，指定使用cryptctl作为密钥获取来源。
- `/etc/fstab`定义解密之后明文设备的挂载点、文件系统参数。

示例：
```
# /etc/crypttab
crypt‑vol /dev/sdb1 none cryptctl
```
> 第三个字段填写`none`，代表密钥不从本地读取，由cryptctl远程获取。

```
# /etc/fstab
/dev/mapper/crypt‑vol  /data  ext4  defaults  0  2
```

完成配置后执行`systemctl daemon‑reload`重载systemd配置。

## 13.4 使用服务端命令查看分区解锁状态
在cryptctl服务端可以查看各个客户端的连接以及卷解锁状态。
```bash
cryptctl‑server status
```
该命令会列出全部注册客户端、客户端主机名、对应LUKS卷、是否已经成功解锁。

## 13.5 手动解锁加密分区
当网络故障、cryptctl服务端不可访问，客户端无法自动拿到密钥完成开机。此时支持手动解锁：
1. 在客户端开机解密提示符界面，选择手动解锁模式。
2. 输入LUKS原始密钥短语，直接解密块设备。
> 该操作绕过cryptctl服务端。需要管理员提前保管好原始LUKS密码，用于灾难恢复。

## 13.6 维护停机流程
当cryptctl‑server需要停机做升级、维护，所有依赖该服务端的客户端将无法开机自动解密磁盘。标准维护步骤：
1. 通知所有业务，准备维护窗口。
2. 全部客户端执行正常关机。
3. 停止`cryptctl‑server`服务，执行维护操作。
4. 维护完成后重新启动`cryptctl‑server`。
5. 依次启动各个客户端主机，客户端正常联网拉取密钥解锁磁盘。

> 不要在客户端运行状态下直接关停服务端：运行中的客户端已经拿到密钥，业务不会中断，但**后续重启就会无法启动**。

## 13.7 为cryptctl‑server服务配置高可用环境
为了避免cryptctl服务端单点故障，可以部署高可用集群环境。
- 使用多台服务器组成cryptctl服务端集群，密钥数据完成多节点同步。
- 使用虚拟IP，客户端仅访问虚拟IP，后端节点故障时自动漂移。
- 集群所有节点使用完全一致的TLS证书与密钥数据库。

> 警告：高可用部署不能降低安全要求，所有集群节点本身都必须磁盘加密，做好访问权限管控。

## 13.8 更多信息
- `man cryptctl‑server`：服务端手册
- `man cryptctl‑client`：客户端手册
- 参考openSUSE官方文档，故障排查cryptctl网络、证书、密钥同步问题。

# 第14章 用户管理
## 14.1 各类账户检查
系统管理员需要定期对系统账户开展审计工作，识别出不必要的账号，降低攻击风险。

### 14.1.1 已解锁账户
找出系统中处于解锁启用状态的账户，确认这些账户全部都是业务运行所必需的。

> **注**：所有不用于交互式登录的系统账号、厂商内置账号都应当被锁定。查看`/etc/shadow`文件，凡是密码字段不以`!`或者`*`开头的条目，就代表该账户处于未锁定状态。

### 14.1.2 闲置账户
找出长期未登录、已经不再使用的账号，及时将其禁用或者直接删除，消除闲置账号带来的安全隐患。长期闲置的账号会成为攻击者的攻击目标。

### 14.1.3 启用密码老化策略
启用密码老化（password aging）机制，配置密码有效期规则：密码到期后强制用户修改密码；密码过期之后账户会被锁定。
相关配置保存在`/etc/shadow`文件中，可以设置密码最大有效期、密码最小修改间隔、密码到期告警提前天数、密码过期宽限期。可以使用`chage`工具修改这些参数。

### 14.1.4 强化密码强制策略
配置更加严格的密码强制规则，设置密码复杂度要求，包含密码最小长度、字符组合规则，阻止用户使用弱口令。该功能由PAM模块实现。

## 14.2 使用PAM管理密码与登录
PAM（可插拔认证模块）负责管控系统密码校验以及登录行为。

### 14.2.1 密码强度
通过对应的PAM模块执行密码强度校验，拒绝简单、容易被破解的密码。当用户执行修改密码操作时，模块会对新密码进行检测。

### 14.2.2 限制历史密码复用
配置策略，禁止用户重复使用此前曾经使用过的旧密码。系统会保存用户历史密码记录，修改密码时进行比对，避免循环复用少量密码。

### 14.2.3 多次登录失败后锁定用户账户
当用户连续多次输入错误密码，自动锁定该用户账户，以此抵御暴力破解登录攻击。

> **重要注意**：`pam_securetty`模块并不适用于OpenSSH。部分SSH登录场景，例如公钥认证，不会完整遍历整套PAM认证栈。除此之外，攻击者可以区分两种返回结果：“密码错误” 和 “策略拒绝登录”，该信息可被用于枚举账号。

### 14.2.4 限制root登录
root账户拥有系统全部权限，应当尽可能限制root直接登录系统的途径。

#### 限制本地文本控制台登录
禁止root账号直接登录本地文本控制台。推荐使用普通用户账号完成登录，之后再通过`su`或者`sudo`命令进行权限提升。

#### 限制图形会话登录
禁止root账号直接登录图形桌面会话。图形界面下以root运行程序会放大安全风险。

#### 限制SSH登录
修改SSH服务配置，禁止root账号直接通过SSH进行远程登录。编辑`sshd_config`设置`PermitRootLogin no`。

#### 限制sudo用户
`sudo`工具允许普通用户以其他用户身份运行命令，最常用的就是以root身份执行操作。
`sudo`的映射配置存放在`/etc/sudoers`文件中。在openSUSE系统上，sudo默认行为是询问root密码，这一点和su命令不同。
遵循最小权限原则，只给确实需要的用户分配sudo权限，不要随意授予全部权限。

### 14.2.5 设置交互Shell会话空闲超时时间
为交互式Shell会话配置空闲超时。当终端长时间没有任何操作时，系统会自动结束该Shell会话。可以防止机器无人看管的情况下被其他人滥用终端。该配置可以全局设置，也可以针对单个用户设置。

### 14.2.6 防范意外拒绝服务
配置资源限制，避免单个用户的进程耗尽系统CPU、内存、打开文件句柄等系统资源，防止由此引发的拒绝服务问题。

##### 系统资源限制示例
可以在`/etc/security/limits.conf`中配置软硬资源限制。软限制（soft limit）用户可以临时调高；硬限制（hard limit）是上限，用户无法超越。

### 14.2.7 显示登录提示横幅
在登录流程中展示登录提示横幅。该提示用于安全警示，也可以满足法律合规要求。
- `/etc/issue`：本地控制台登录前展示
- `/etc/issue.net`：SSH远程登录前展示
- `/etc/motd`：登录成功之后展示的消息

> 不要在横幅内泄露系统版本、内核版本等敏感信息。

### 14.2.8 连接记账工具
启用连接记账审计工具。记账工具可以记录用户登录会话、用户执行的进程，用于后期安全审计、事件追溯。使用`acct`软件包实现该功能。

# 第15章 限制 cron 和 at
cron系统用于按照预定义的时间，在后台自动执行命令。想要了解cron的更多信息，请参考《管理员指南》中cron软件包相关章节。

攻击者如果拿到普通用户账号权限，就可以利用cron或at来设置后台恶意任务，实现持久化驻留。因此有必要限制哪些用户有权限创建定时作业。

## 15.1 限制 cron守护进程
`/etc/cron.allow` 文件用于指定允许通过cron创建作业的用户列表。该文件在系统默认状态下并不存在。当该文件不存在时，**所有用户都可以创建cron定时任务**，只有写在`cron.deny`中的用户会被拒绝使用cron。

> 规则逻辑：
> 1. 如果`cron.allow`文件存在，仅该文件内列出的用户允许使用cron，`cron.deny`会被直接忽略。
> 2. 如果`cron.allow`不存在，则读取`cron.deny`，名单中的用户被禁止使用cron，其余用户允许。
> 3. root用户不受这两个文件限制，始终可以使用cron。

如果你想要禁止除root以外的所有用户创建cron作业，请按照下面步骤操作：
1. 创建空的`/etc/cron.allow`文件：
```bash
sudo touch /etc/cron.allow
```
2. 将需要允许使用cron的用户名逐行写入该文件。示例：
```bash
sudo echo "tux" >> /etc/cron.allow
```

### 验证配置效果
使用已经写入`cron.allow`的普通用户执行编辑定时任务命令：
```bash
crontab -e
```
输出提示类似：`no crontab for tux - using an empty one`，代表允许操作。

再使用一个不在`cron.allow`列表内的用户执行同样命令。系统会返回权限拒绝提示，不允许编辑crontab。

> **注意**：创建`cron.allow`只会阻止用户**新增**crontab任务，**不会删除用户已经存在的旧定时任务**。为彻底阻断旧任务执行，你还需要手动删除`/var/spool/cron/tabs`目录下其他普通用户的crontab文件。

> **提示：考虑改用systemd定时器单元**
建议优先考虑使用`systemd timer`定时器单元。它功能更强、可靠性更高。默认情况下普通用户无法通过它在未登录状态下运行代码，能够限制用户在离线状态下对系统执行操作，安全性更佳。更多内容参考《参考指南》systemd定时器章节。

## 15.2 限制 at调度器
at作业执行系统允许用户调度一次性运行的任务。`at.allow`文件指定可以使用at调度任务的用户列表。该文件默认不存在；文件不存在时，所有用户都可以提交at任务，仅`at.deny`中的用户被拒绝。

规则逻辑与cron完全一致：
1. 如果`at.allow`存在，只有文件内列出的用户可以使用at，忽略`at.deny`。
2. 如果`at.allow`不存在，读取`at.deny`，拒绝名单内用户。
3. root不受限制，始终可以使用at。

要禁止除root以外全部用户使用at调度作业，执行以下步骤：
1. 创建空的`/etc/at.allow`：
```bash
sudo touch /etc/at.allow
```
2. 将需要授予权限的用户名写入文件：
```bash
sudo echo "tux" >> /etc/at.allow
```

### 验证配置效果
使用已授权用户尝试提交一次性任务：
```bash
at 00:00
```
出现`at>`交互提示符，说明权限生效，按下`Ctrl‑C`退出。

使用未授权的用户执行相同命令，会输出提示：`You do not have permission to use at`（你没有权限使用at）。

> **备注：卸载at软件包**
如今at工具的使用场景已经不多。如果你的业务没有实际需求，可以直接卸载at软件包，从根源上消除该攻击面。

# 第16章 Spectre/Meltdown checker（幽灵/熔断漏洞检测工具）
## 16.1 使用 spectre‑meltdown‑checker
Spectre（幽灵）与Meltdown（熔断）是影响多款现代处理器的硬件侧信道漏洞。这类漏洞能够让恶意进程绕过内存隔离机制，读取本无权访问的内存内容。`spectre‑meltdown‑checker` 是一个Shell脚本工具，用于检查本地系统是否容易受到这些漏洞的影响，同时确认当前系统内核所启用的缓解措施是否生效。

> **警告**
该工具仅用于检查缓解措施是否已经部署到位，**它无法修复硬件本身存在的缺陷**。部分缓解机制会带来一定的性能损耗；要彻底根除漏洞，需要更换存在缺陷的CPU硬件。

在openSUSE Leap系统中，先安装对应的软件包：
```bash
zypper in spectre-meltdown-checker
```

必须以root管理员身份运行该脚本，执行完整检测：
```bash
spectre-meltdown-checker
```

脚本会输出一份检测报告，逐项评估各类CPU推测执行漏洞状态，包括：
- Meltdown（CVE‑2017‑5754）熔断漏洞
- Spectre Variant 1（CVE‑2017‑5753）幽灵1号变体，边界检查绕过
- Spectre Variant 2（CVE‑2017‑5715）幽灵2号变体，分支目标注入
- Spectre Variant 4（CVE‑2018‑3639）幽灵4号变体，推测存储绕过
- L1TF / Foreshadow（CVE‑2018‑3620）L1缓存漏洞
- MDS系列漏洞（CVE‑2019‑11091、CVE‑2019‑11098等）
- SRBDS（特殊寄存器缓冲区数据采样）以及后续其他衍生的CPU侧信道漏洞

每一项检测会返回三种结果状态：
1. **VULNERABLE（存在漏洞）**：未配置缓解措施，系统易遭受攻击。
2. **MITIGATED（已缓解）**：内核补丁、CPU微代码更新已部署，风险得到抑制。
3. **NOT VULNERABLE（不受漏洞影响）**：CPU硬件本身不存在该漏洞。

### 常用运行参数
生成适合程序解析的批处理（机器可读）输出，方便集成到自动化脚本：
```bash
spectre-meltdown-checker --batch
```

将完整检测报告重定向保存为文本文件，便于归档与排查：
```bash
spectre-meltdown-checker > spectre-report.txt
```

仅读取系统文件做离线分析，不做任何运行时内存探测：
```bash
spectre-meltdown-checker --offline
```

> **重要提示**
部分漏洞缓解依赖CPU微代码更新。微代码可以由系统固件BIOS/UEFI提供，也可以由内核加载。即便内核已经打上补丁，如果CPU微代码版本老旧，部分缓解方案依旧无法生效。

在虚拟机环境中，一部分检测项结果取决于宿主机CPU硬件以及宿主机的缓解配置。虚拟机内部操作系统能够执行的缓解手段会受到限制。

## 16.2 更多信息
- `man spectre‑meltdown‑checker`：查看工具手册页，获取全部可用参数说明。
- SUSE安全公告知识库，可以根据CVE编号查询对应的补丁包、升级建议。
- 内核文档：`/usr/share/doc/kernel‑doc*/speculation‑melt‑spectre.rst`，文档详细讲解内核各项推测执行漏洞缓解机制的工作原理。
- 工具上游项目仓库，查阅新增CPU漏洞的检测更新说明。

# 第17章 使用YaST配置安全设置

1. **工作站（Workstation）**
适用于桌面工作站，在安全性与易用性之间取得平衡，面向普通桌面用户。
2. **服务器（Server）**
面向服务器主机，强化安全约束，牺牲部分便捷性功能，适用于本地、远程访问的服务器。
3. **安全加固（Secure）**
最高安全等级，限制最为严格，用于高安全等级环境。该模式会限制很多常规操作，会对使用便捷度造成影响。

> 注意：应用任意一套预定义模板后，请逐项核对所有参数，确认符合你的业务环境，不可完全依赖模板默认值。

## 17.3 密码设置
容易被猜测破解的密码是主要安全风险。密码设置对话框用于强制系统只能使用安全性合格的密码。
- **检查新密码**
开启该选项后，如果新密码出现在密码字典中，或是普通专有名词，系统会发出警告。
- **可接受的最小密码长度**
如果用户设置的密码短于此处指定长度，系统会发出警告。
- **需要记忆的旧密码数量**
开启密码老化功能时，系统会记录指定条数的历史旧密码，禁止用户重复使用这些旧密码。
- **密码加密方式**
选择密码哈希加密算法。一般情况下，无需修改默认的Blowfish算法。
- **密码有效期**
设置密码最小、最大有效天数，开启密码过期机制。
设置最小有效期大于0天，可以防止用户改完密码立刻又改回旧密码，规避密码过期策略。
填入`0`和`99999`这两个数值，可以关闭密码过期功能。
- **密码过期提前告警天数**
密码到期之前，提前多少天向用户发出修改密码提醒。

> 重要提示：本页面的策略**仅对之后新建/修改的密码生效**。不会修改系统已有账户的密码老化属性；存量账户请使用`chage`命令单独配置。

# 第18章 Polkit认证框架
## 18.1 概念概述
Polkit是一个用于系统级权限管控的认证框架。它定义了非特权进程如何与特权进程进行交互。借助Polkit，管理员可以精细化管控：普通用户无需完整root权限，就能够执行部分需要管理员权限的操作；同时也可以限制用户禁止执行某些特权操作。
Polkit不是一套传统的set‑uid程序，它将权限决策逻辑从应用程序中剥离，交由独立的授权服务处理。策略规则集中管理，管理员可统一修改，不需要修改各个应用程序本身的代码。

### 认证代理（The authentication agent）
Polkit本身并不提供图形或密码输入弹窗。认证代理负责向用户展示身份验证对话框，收集用户密码或者凭证，再把凭证提交给Polkit框架完成校验。
桌面环境（如GNOME、KDE）自带对应的Polkit认证代理；非图形控制台环境需要手动运行代理程序。如果没有可用的认证代理，需要特权的操作会直接执行失败。

### Polkit的配置
Polkit的配置由两部分组成：
1. **策略文件（.policy）**：XML格式，定义各个操作（action）的默认授权行为，软件包安装时会附带这些文件。
2. **JavaScript规则文件（.rules）**：在`/etc/polkit‑1/rules.d/`目录下，管理员编写，用来覆写默认策略、实现自定义的复杂授权逻辑。

> 路径说明：
> - 系统自带策略：`/usr/share/polkit‑1/actions/*.policy`
> - 管理员自定义规则：`/etc/polkit‑1/rules.d/*.rules`

### Polkit工具集（Polkit Utilities）
Polkit提供命令行工具，方便管理员查询、测试授权策略：
- `pkaction`：列出全部已注册的Polkit操作ID（action id）。
- `pkcheck`：检查某个进程是否有权限执行指定的Polkit操作。
- `pkexec`：以Polkit授权的身份运行程序，替代部分sudo使用场景。

## 18.2 授权类型（Authorization types）
每一项Polkit操作都可以定义多种授权结果类型：
1. **yes（允许）**：直接允许执行，不需要身份验证。
2. **no（拒绝）**：直接拒绝执行该操作。
3. **auth_self**：需要执行操作的本地用户验证自身密码；root密码不可用。
4. **auth_self_keep**：验证自身密码，短时间内缓存授权，短时间内再次执行同一操作无需重复输入密码。
5. **auth_admin**：需要管理员用户输入管理员密码，执行操作的普通用户本身不需要是管理员。
6. **auth_admin_keep**：输入管理员密码，授权会被短暂缓存，短时间重复调用不需要再次输入密码。

### 隐式授权（Implicit Authorizations）
隐式授权是Polkit内置规则：root用户执行所有Polkit操作，默认直接允许（yes），不需要认证。

### SUSE默认特权（SUSE default privileges）
openSUSE预先配置了一套默认Polkit策略。部分操作允许本地控制台登录的普通用户直接执行，不需要输入密码，例如挂载可移动U盘、调整屏幕亮度、网络管理等。远程会话（SSH等）不会继承这类宽松权限。

## 18.3 查询特权（Querying Privileges）
使用`pkaction`命令查看系统全部可用的Polkit操作。
```bash
pkaction
```
查看单个action的详细描述、默认授权设置：
```bash
pkaction --action-id org.freedesktop.udisks2.filesystem‑mount‑system
```
使用`pkcheck`测试某个进程是否拥有对应操作权限。

## 18.4 修改Polkit配置（Modifying Polkit Configuration）
> ⚠️警告：修改Polkit策略错误，会造成权限异常：普通用户获得过高权限，或者正常系统功能无法使用。修改前务必备份原文件。

### 18.4.1 覆写Polkit策略文件（Overriding Polkit policy files）
**不要直接编辑 `/usr/share/polkit‑1/actions/` 下的原始policy文件**。软件包更新会覆盖、删除你做的修改。

正确覆写方式：
在 `/etc/polkit‑1/actions/` 目录创建同名的policy文件。该目录的文件优先级高于`/usr/share/polkit‑1/actions/`，软件升级不会改动该目录。

### 18.4.2 添加JavaScript授权规则（Adding JavaScript authorization rules）
`.rules` 文件使用JavaScript语法，放置在`/etc/polkit‑1/rules.d/`，文件名以数字前缀排序（例如`50‑my‑custom.rules`），数字越小越优先加载。
规则可以做复杂逻辑：按用户、用户组、会话类型（本地控制台 / SSH远程）、时间条件，动态修改授权结果。

示例极简规则片段：
```javascript
polkit.addRule(function(action, subject) {
    if (action.id == "org.freedesktop.udisks2.filesystem‑mount‑system" &&
        subject.isInGroup("storage")) {
        return polkit.Result.YES;
    }
});
```
该示例允许storage用户组的用户挂载系统磁盘，无需密码。

> 提示：语法写错会导致整个rules文件失效，查看系统journal日志排查错误：`journalctl -u polkit`

### 18.4.3 修改SUSE默认特权（Modifying the SUSE default privileges）
SUSE自带自定义规则文件，用来实现发行版默认宽松权限。你可以在`/etc/polkit‑1/rules.d/`添加更高数字编号的rules文件，覆盖SUSE预设行为。不要直接修改SUSE自带的规则文件，包升级会覆盖改动。

### 18.4.4 恢复SUSE默认特权（Restoring the SUSE default privileges）
如果你手动添加自定义rules造成策略混乱，删除你手动创建的自定义`.rules`文件即可恢复系统默认；
如果修改过`/etc/polkit‑1/actions/`下覆写文件，同样删除这些文件。重启polkit服务：
```bash
systemctl restart polkit
```

> 重要补充：Polkit策略变更**即时生效**，不需要重启服务；但如果rules存在语法错误，重启polkit有助于把错误输出写入journal日志方便排错。

# 第19章 Linux中的访问控制列表（Access control lists）
## 19.1 传统文件权限
传统UNIX文件权限模型，将访问主体分为三类：文件属主（owner）、属组（group）、其他所有用户（other）。每一类分别拥有读、写、执行三种权限位。

### setuid位（SUID）
当可执行文件设置setuid位，程序运行时将临时使用**文件所有者**的UID，而不是运行该程序的用户UID。
典型示例：`/usr/bin/passwd`，普通用户执行passwd修改密码时，会临时拥有root权限，才能够修改`/etc/shadow`。
> 安全风险：不安全的setuid程序是常见攻击向量，系统应当定期审计setuid文件。

### setgid位（SGID）
setgid分为两种行为：
1. **作用于可执行文件**：程序运行时，进程的组ID采用文件属组的GID，而非调用用户的组ID。
2. **作用于目录**：在该目录下新建的文件/子目录，会自动继承此目录的属组，而不是继承创建者的默认用户组。多用于协作共享目录。

### 粘滞位（sticky bit）
粘滞位主要应用在目录上。开启粘滞位的目录，目录内的文件仅允许**文件的属主、目录属主、root**删除或重命名。
最典型例子是`/tmp`目录。所有用户均可向/tmp写入文件，但普通用户不能删除其他人创建的临时文件。

### ACL的优势（Advantages of ACLs）
传统ugo（user‑group‑other）权限模型粒度有限，只能针对三类主体设置权限。
ACL（访问控制列表）可以对**多个指定用户、多个指定用户组**分别配置独立权限，突破传统ugo的限制。
例如：某个目录属主为root，属组为adm，你可以单独给用户tux授予读写权限，同时不给其他全部用户开放权限，传统ugo权限无法做到这一点。

## 19.2 定义（Definitions）
- **ACL条目（ACL entry）**：ACL中的一条权限规则，格式为`类型:标识符:权限`，类型可以是user、group、mask、other。
- **访问ACL（Access ACL）**：作用于文件/目录本身，控制该对象的访问权限。
- **默认ACL（Default ACL）**：**仅对目录生效**。目录设置默认ACL之后，在此目录中新创建的文件、子目录，会自动继承这套默认ACL规则。默认ACL不会对目录自身生效。
- **mask**：ACL掩码。mask定义ACL里用户、组能够获得的**最大有效权限**。不管单条ACL条目授予什么权限，最终生效权限不能超过mask设定。other权限不受mask约束。

## 19.3 ACL的处理（Handling ACLs）
### 19.3.1 ACL条目与文件模式权限位（ACL entries and file mode permission bits）
当文件设置了ACL，传统ugo权限位依然存在，但会与ACL互相影响：
1. owner权限位，等价于ACL中user::（空标识符，代表文件属主）的权限。
2. group权限位，不再代表文件属组的实际权限；此时group位存放**mask值**。
3. other权限位等价ACL中other::权限。

> 使用`ls -l`查看文件时，如果文件带有ACL，权限字符串末尾会显示`+`加号，标识该对象配备ACL。
示例：
```
-rw-rw-r--+ 1 root users  0 Sep  1 10:00 testfile
```
末尾`+`表示此文件拥有访问控制列表。

### 19.3.2 带有ACL的目录（A directory with an ACL）
举例，目录`/srv/share`配置访问ACL：
- user::rwx（属主root：读写执行）
- user:tux:rwx（用户tux：读写执行）
- group::r‑x（文件属组users：读、进入目录）
- group:devel:r‑x（devel组：读、进入目录）
- mask::rwx（掩码最大权限rwx）
- other::‑‑‑（其他所有用户无任何权限）

mask设置为rwx，所以tux、devel组的权限可以完整生效。
如果mask改为r‑x，即便user:tux配置rwx，tux实际只能拥有r‑x权限，写权限会被mask截断。

### 19.3.3 带有默认ACL的目录（A directory with a default ACL）
给目录同时配置**访问ACL + 默认ACL**。
访问ACL管控目录本身；默认ACL只用来传给子对象。
在该目录下新建文件或子目录，系统自动复制默认ACL作为新对象的访问ACL。新建子目录还会继承这份默认ACL。

> 注意：新建文件不会继承setuid/setgid/sticky bit，仅继承ACL规则。

### 19.3.4 ACL检查算法（The ACL check algorithm）
当进程访问带有ACL的文件对象，内核按顺序校验：
1. 如果进程UID等于文件属主UID → 使用ACL user::权限。结束判断。
2. 否则，检查进程UID是否匹配任意一条`user:用户名`ACL条目。匹配则取该条权限，受mask约束。结束判断。
3. 否则，判断进程的任意一个附属GID，是否匹配任意group类ACL条目。匹配后，收集全部匹配组条目的权限，取权限的并集，结果受mask掩码限制。结束判断。
4. 以上全部不命中，则使用other::的权限。

> 关键点：组ACL是取**权限并集**，多个组同时匹配时，只要某一条组条目授予读，就获得读权限。

### 19.3.5 应用程序对ACL的支持（ACL support in applications）
不是全部工具、应用程序都完整识别ACL。
- `cp`、`mv`：特定参数下才保留ACL；不加参数复制文件会丢失ACL。`cp -a`可以保留ACL。
- tar：默认不归档ACL，需要`--acls`参数才保存、恢复ACL。
- 很多第三方备份工具需要开启专门选项，否则只备份传统ugo权限，丢失ACL信息。

> 风险提示：备份恢复时如果丢失ACL，会带来严重权限安全问题。做备份前确认备份软件支持ACL扩展属性。

## 19.4 更多信息
- `man acl`：ACL总览手册
- `man getfacl`：读取ACL命令手册
- `man setfacl`：设置ACL命令手册

常用命令示例：
```bash
# 查看文件ACL
getfacl /srv/share
# 设置用户tux对目录读写执行ACL
setfacl -m u:tux:rwx /srv/share
# 设置默认ACL（仅目录）
setfacl -m d:u:tux:rwx /srv/share
# 删除一条ACL
setfacl -x u:tux /srv/share
# 清除全部ACL
setfacl -b /srv/share
```

# 第20章 使用AIDE实现入侵检测
## 20.1 为什么要使用AIDE？
AIDE（Advanced Intrusion Detection Environment，高级入侵检测环境）是一款文件完整性检测工具。它会根据基准数据库记录系统文件、目录的各项属性，后续可以将系统当前实际状态与数据库记录做比对。

AIDE会校验的文件属性包括：文件大小、权限位、属主、属组、时间戳、文件哈希校验值（md5、sha1、sha256等）。

当系统遭受入侵之后，攻击者经常会修改系统二进制程序、配置文件、脚本，植入后门。普通用户很难手动发现这类改动。AIDE可以检测出文件被篡改。

> **重要警告**：AIDE本身**不能阻止入侵发生**。它仅用于检测入侵发生后文件是否遭到篡改。如果AIDE自身的二进制程序或者AIDE数据库遭到攻击者篡改，那么检测结果将完全失效。
> 最佳安全实践：将初始化生成的AIDE基准数据库拷贝到**离线只读介质**（U盘、光盘）保存，不要只存放在被监控的本机磁盘上。

## 20.2 搭建AIDE数据库
1. 安装AIDE软件包
```bash
zypper in aide
```
2. 主配置文件路径：`/etc/aide/aide.conf`
配置文件定义需要监控的目录、需要排除不检测的目录、需要比对哪些文件属性、数据库存放路径。

> 配置说明：
> - 选择监控对象：填写需要保护的系统目录，例如 `/bin`、`/sbin`、`/etc`、`/usr/bin`。
> - 排除目录：频繁变化的目录需要排除，例如 `/proc`、`/sys`、`/tmp`、`/var/tmp`、日志目录`/var/log`，这些目录文件会正常频繁变动，若加入监控会产生大量误报。

3. **初始化生成基准数据库**
> ⚠️务必保证执行初始化时系统处于干净、未被入侵的状态。
```bash
aide --init
```
默认会生成新数据库文件：`/var/lib/aide/aide.db.new`。
生成完成后，你必须将该文件重命名，作为正式比对基准库：
```bash
mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db
```

> 强烈建议：复制这份`aide.db`基准数据库到离线存储设备。一旦主机被攻陷，本机数据库有可能被篡改。

## 20.3 在本地执行AIDE检查
执行完整性校验，将当前系统文件状态与AIDE基准数据库进行比对：
```bash
aide --check
```

输出说明：
- **Added**：检测到新增加的文件。
- **Removed**：数据库记录存在，但当前系统找不到该文件，文件已被删除。
- **Changed**：文件属性、哈希值发生改变。

> 区分告警是合法变更还是恶意篡改：
系统正常软件更新、管理员手动修改配置文件，同样会触发Changed告警。每次执行zypper软件包升级之后，AIDE的数据库就会过期，需要更新数据库。

当确认文件改动属于管理员合法操作，更新AIDE数据库：
```bash
aide --update
```
该命令生成`aide.db.new`，再把它替换旧数据库。
```bash
mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db
```

> 提示：可以配置cron定时任务，定期自动运行`aide --check`，把检查报告输出发送邮件给管理员。

## 20.4 独立于本机系统执行检查（System independent checking）
这是高安全等级推荐的检查方式。
如果系统已经被入侵，本机上的AIDE二进制文件有可能被攻击者替换篡改，此时本机运行的aide‑‑check结果不可信。

独立检查操作步骤：
1. 使用干净的openSUSE Live介质（U盘/光盘）启动计算机。
2. 挂载本机被监控系统磁盘分区。
3. 使用Live介质环境里**干净未被篡改的aide程序**，读取**离线保存的原始基准aide.db数据库**，对挂载的主机磁盘文件做完整性比对。

该方式完全不使用主机磁盘上的aide二进制，规避程序被后门篡改带来的检测失效风险。

## 20.5 更多信息
- `man aide`：AIDE工具手册页。
- `/etc/aide/aide.conf`：配置文件自带大量注释示例。
- `/usr/share/doc/packages/aide`：软件包附带文档，包含配置模板。

> 补充安全提示：
AIDE只检测文件系统对象。它无法检测内存中正在运行的恶意进程、内核级rootkit。AIDE需要和日志审计、系统防火墙、其他安全工具搭配使用，构成完整防御体系。
